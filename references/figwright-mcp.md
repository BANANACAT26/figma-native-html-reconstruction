# Figwright / Figma MCP 使用约定

## 先验证能力，不写死版本假设

先执行工具列表和能力探测，确认实际的读取、节点信息、截图、原生导出方法及参数，不凭名称猜 schema。但 tools/list 是**可选**的能力发现元数据：工具名由 SOP 契约固定，发现失败绝不能阻塞整条重建。

推荐主路线：

1. 读页面/文档结构，确定画板。
2. 读取目标画板完整子树。
3. 需要时补读具体节点与实时可见性。
4. 通过插件原生导出独立 TEXT-free 节点。
5. 用实时截图核对可视内容，而不是只看序列化 bbox。

## tools/list 弹性策略

实跑中出现过编辑器侧 tools/list 反复超时而 tools/call 完全正常，也曾出现"超时"实为请求未先 send 就等响应。因此客户端对 tools/list：

- 有界重试：可配单次超时与重试次数（环境变量 `FIGWRIGHT_TOOLS_LIST_TIMEOUT`、`FIGWRIGHT_TOOLS_LIST_RETRIES`），失败后退化为 degraded（`tools={}`、`tools_list_status=degraded`）并继续按契约工具名调用，不抛异常中断。
- 显式跳过：编辑器侧卡住时设 `FIGWRIGHT_SKIP_TOOLS_LIST=1`，直接跳过发现。
- JSON-RPC 纪律：任何请求必须先 `send` 再 `call_raw` 等对应 id 响应；未发送就等待会表现为假性超时。
- 只有 initialize 握手失败才中止会话。

## 会话串行约束

一个 session id 绑定的 Figma 编辑器会话**串行处理 tools/call**。live 读取、导出、复验对同一 session 必须串行排队；禁止两个 FW 实例或两路 live 复验并发打同一 session id，否则 get_node 会在插件端排队数十分钟无返回。多画板 live 复核复用会话逐板串行，或换独立 session。

## 只读环境

Dev Mode 可能拒绝 clone、hide-text 等写操作。不要把“先复制画板再隐藏文字”作为必要步骤。直接在内存中遍历节点并收集不含 TEXT 的最大子树，再显式导出这些节点。

## 为什么不用整板 SVG 回传作为主路线

- 大画板包含大量图片、路径和效果，回传可能超时。
- 整板回传容易重新引入“整板图代替网页”的边界问题。
- 节点级结构化数据更适合增量修复、几何审计和哈希追溯。

真实实践中整板 SVG 回传两次超时，因此只保留为小范围矢量或独立连接器的备选。

## 为什么不依赖 GUI 自动化

AX 点击返回成功不代表 Figma 内真实选择或展开状态已改变。若 MCP 能读取同一事实，就不要用 GUI 作为主数据源。不得仅凭一次点击或截图未变判断操作成功/失败；读取实际状态后再行动。

## 数据保存

每次读取保存：工具名、参数、时间、原始响应、画板 ID、文件/页面版本线索。不要把长响应反复粘进上下文；保存 JSON 后用脚本抽取所需字段。

## 常见映射

- 页面顶层 VECTOR 不一定是画板。
- `visible=true` 不排除被上层覆盖或祖先裁剪。
- 节点注册 bbox 不一定是旋转后实际像素边界。
- 静态设计缓存可能落后，可见性最终以 live 为准。
- `exportAsync` 生成的是独立节点视觉，不等于已确认浏览器中的摆放位置。
